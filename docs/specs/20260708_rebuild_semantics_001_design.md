## 0. 背景（2026-07-05 実機テスト由来・改修候補⑩）

「☁ クラウドから完全再構築」は、クラウドの大会記録から各会員の「前回クラス・最終参加・参加履歴」を**再計算して名簿へ反映**する導線（#551）。ただし**端末側の新しい参加記録は巻き戻さない（ローカル温存）**仕様のため、端末にテスト残骸・重複登録があると再構築後も表示が狂う。実テストでは **マスタリセット→再構築の完全初期化**で解消した（Safari 側で実証）。

課題は2つ:

1. **語感の齟齬**: ボタン名「**完全**再構築」／機能名の「完全」が、実際の「ローカル温存（端末の新しい記録は残す）」仕様と食い違い、利用者が「クラウドに完全一致する」と誤解する。温存仕様が UI 文言から読み取れない。
2. **完全一致の導線が無い**: 「本当にクラウドの状態へ揃えたい（端末残骸を捨てたい）」ユースケースに対し、現状は「マスタリセット」と「再構築」を利用者が手動で2段実行する必要があり、手順が知識依存。

## 1. 現状の挙動（正確な事実確認）

- `rebuildMasterFromCloud`（#551・純関数）はクラウド entries から派生属性（last_class / 最終参加日 / tournament_ids 等）を**再計算**し名簿へ反映する。**氏名・ふりがな・区分・市町村・削除状態は変更しない**。端末ローカルの未送信参加記録も**保持**する（＝温存）。
- 現行 confirm（L4944）は既に温存を明記している:
  > 「クラウドの大会記録から、各会員の『前回クラス・最終参加・参加履歴』を再計算して名簿へ反映します。氏名・ふりがな・区分・市町村・削除状態は変更しません。**端末に未送信の直近の参加記録は巻き戻しません。** 再構築しますか？」
- 一方、**ボタンの表示名**は「☁ クラウドから完全再構築（参加履歴も再計算）」で「完全」が残り、confirm を読む前に誤解を生む。
- マスタリセットには既に強確認 UI（`openMasterResetModal`＝バックアップ確認チェック＋「リセット」文字入力＋赤 danger ボタン・disabled ガード）が存在し、「完全一致」オプションの土台に再利用できる。

→ 本 Issue は「温存仕様を UI で読めるようにする（文言）」と「完全一致の安全な一括導線を足す（任意・危険度設計）」の2点に絞れる。**再計算ロジック（#551）は無改変**。

## 2. 決定を要する論点（作者確定待ち・AskUserQuestion 想定）

- **Q1 ボタン名の寄せ方**: (A) 「完全」を外し実態に寄せる（例「☁ クラウドから名簿を再計算（参加履歴を反映）」）／ (B) 「完全」を残しツールチップ・confirm で温存を強調。→ **推奨 (A)**（語感の誤解を根絶）。
- **Q2 「クラウドに完全に合わせる」オプションの要否**: (A) 今回は文言明確化のみ・完全一致導線は見送り／ (B) マスタリセット→再構築の一括導線を新設（danger 強化）。→ 実機で「完全初期化で解消」した実績があるため **(B) を推奨**するが、危険度が高くリスクは §4 で明示。
- **Q3 完全一致導線の配置**: 名簿メンテナンスの `<details>` 内・既存マスタリセットの隣に「☁ クラウドの状態に完全に合わせる（端末の記録を破棄）」として置く。

## 3. 設計 — Phase 分割

### Phase 1（低リスク・文言のみ）: 温存仕様の明文化

副作用ゼロの表示文言変更のみ。

1. **ボタン名変更**（`masterRebuildBtn` L3931）: 「完全」を外す（Q1=A 採用時）。`id` は不変＝既存 bind を温存。
2. **ツールチップ／補助文**: ボタンに `title` を付与し「端末の新しい記録は残したまま、クラウドの大会記録で参加履歴を再計算します」。
3. **confirm 文言の微修正**（L4944）: 温存の一文を強調位置へ（「**この端末の新しい参加記録はそのまま残ります**」）。STYLE-GUIDE の「この端末に保管／みんなで共有」対語体系に整合。
4. ヘルプ/文言は STYLE-GUIDE 準拠。破壊的操作ではないので danger 化しない（Enter=OK 維持・#606 appConfirm）。

### Phase 2（高リスク・任意）: 「クラウドに完全に合わせる」一括導線

Q2=B 採用時のみ。**マスタリセット→再構築を1導線に束ねる**（既存関数の再利用・新規破壊ロジックは書かない）。

- 新ボタン「☁ クラウドの状態に完全に合わせる（端末の記録を破棄）」を名簿メンテナンス details 内へ追加。
- クリック→ **既存 `openMasterResetModal` の強確認 UI を再利用**（バックアップ確認チェック＋「リセット」入力＋赤 danger ボタン）。文言だけ「完全一致」用に差し替え、確認語は誤操作防止のため専用語（例「クラウドに合わせる」）を要求。
- 確認通過→ `resetMaster` 相当（既存）→ 続けて `rebuildMasterFromCloudUI` を自動連鎖。途中失敗は fail-soft（status 表示・部分適用を避けるため「リセット後に再構築失敗」時のリカバリ文言を明示）。
- **大会進行中ガード**: `state.started`（いずれかのクラスが開始済み）の場合は実行不可＝ボタン disabled＋注記（当日運営中の破壊操作を封じる）。
- クラウド接続前提（未ログイン時は disabled＋「ログインが必要です」）。

## 4. リスクとトレードオフ（設計に明記）

- **温存 vs 完全一致**: 温存はデータ安全（端末の未送信分を失わない）だが残骸が残る。完全一致は残骸を消せるが、**削除 push 未達／未送信の正当な参加記録も失う窓**がある（#549 と同型＝ローカル正本 vs クラウド正本のトレードオフ）。
- **削除 push 未達時の巻き戻り窓**: クラウドへ未反映のローカル変更は完全一致で消える。Phase 2 は「先にバックアップ（強確認 UI のチェック必須）」で緩和するが、**復元経路（バックアップ import）を confirm 文言で明示**する。
- **部分適用**: リセット成功→再構築失敗だと名簿が空に近い状態で残る。fail-soft の status に「再構築に失敗しました。『☁ …再計算』を再実行するか、バックアップから復元してください」を出す。
- Phase 2 は破壊的操作の連鎖ゆえ **Review Level L3**（リセット系・#606 の danger 既定キャンセル方針を踏襲）。Phase 1 は表示のみで L2 相当。

## 5. 受入条件

1. ボタン名・ツールチップ・confirm から「端末の新しい記録は残る（温存）」が読み取れる（Q1 決定を反映）。
2. 「完全」の語が温存仕様と矛盾しない（外すか、温存明記で解消）。
3. （Phase 2 採用時）完全一致導線はバックアップ確認＋専用確認語＋大会進行中ガード＋未ログイン disabled を満たす。
4. 再計算ロジック（#551 `rebuildMasterFromCloud`）は無改変。当日運営コア無改変・cloud-write は既存経路のみ（新規書き込み無し）。
5. `bash test/run_tests.sh shogi_v4.html` WARN=0 維持＋（実装時）文言/ガードのユニット/GOLDEN。

## 6. テスト計画（実装フェーズ・架空データのみ）

- Phase 1: ボタン `title`／confirm 文言に温存フレーズが含まれる静的アサート。confirm 経路が `rebuildMasterFromCloudUI` を呼ぶ（挙動不変）回帰。
- Phase 2: (a) `state.started=true` でボタン disabled（純ガード関数の GOLDEN） (b) 未ログインで disabled (c) 確認語一致でのみ実行可（strict equality） (d) リセット→再構築の連鎖順序（mock で呼び出し順を検証） (e) fail-soft（再構築失敗時に status メッセージ）。

## 7. スコープ外（将来）
