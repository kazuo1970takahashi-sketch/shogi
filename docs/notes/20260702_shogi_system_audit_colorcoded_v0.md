## 0. 総評 — 「継ぎ接ぎ」の実態

診断結果を先に言うと、**芯は継ぎ接ぎではない。表皮が継ぎ接ぎ**である。

- **芯（データ・ロジック層）は堅牢**: normalize 往復恒等・保存の多層防御・テスト 746 PASS/WARN0・GOLDEN 56。
  スライス開発の規律（設計メモ→Draft PR→独立レビュー）が効いており、ロジックの一貫性は高い。
- **表皮（UI・文言・通知）に増築痕が集中**: 通知手段が5系統併存、保存系ボタンが4種、
  インライン style 520 箇所、絵文字ありボタン 11 vs なし 62、当日アプリと app/ で配色が別物。
  これが「ごちゃごちゃ感」「一貫性のなさ」の正体。

つまりジャンプアップの足がかりは**機能追加ではなく「UI 規約の制定と表皮の統一」**にある。

## 2. 🟡 改善が必要（機能はあるが体験を損ねているもの）

優先度順。★=ごちゃつき解消への効き目大。

### 🟡-1 ★ 通知・確認手段の乱立（一貫性欠如の最大要因）
実測: `alert` 61・`confirm` 28・`showMsg` 119・`setStatus` 52・console.warn 59。
同じ「操作の結果を伝える」のに、ブロッキングの alert と控えめな showMsg が場面ごとにバラバラに選ばれている。
**処方**: 通知4分類のルールを決めて段階的に置換 —
①破壊的操作の事前確認=confirm（統一文体「〜します。よろしいですか？」）
②成功=非ブロッキング toast/showMsg（alert からの移行）
③進行状況=status 行
④開発者向け=console。
一度に全置換せず「1タブ=1スライス」で移行（挙動変更なので文言テストは緩く pin）。

### 🟡-2 ★ 保存系4系統の概念が画面に出ていない
「自動保存（localStorage）／📋名簿を更新（マスタ同期）／バックアップ（JSON）／☁クラウドへ送信」の4つは
役割が違うのに、ユーザーから見ると「保存っぽいボタンが4つ」。PR#357 でファイル名・自動判別は改善済みだが、
**「どれが必須で、どれで復旧できるか」の全体像**は依然どこにも表示されない。
**処方**: ヘッダに**保存状態バー1行**（例: 「保存済 14:32｜名簿同期済｜バックアップ 13:05｜☁未送信」）を追加し、
タップでヘルプ（save 系統の説明 topic）へ。ボタンを減らすのではなく**状態を見える化**して迷いを消す。

### 🟡-3 ★ 見た目のトークン不統一（ごちゃつきの視覚的要因）
実測: インライン style 520 箇所・絵文字ありボタン 11 vs なし 62・btn-primary 19/btn-danger 2/btn-success 1・
当日アプリ #1F3864 vs app/ #2b6cb0 で配色が別物。
**処方**: (a) `docs/STYLE-GUIDE.md` を制定（🔵-1）→ (b) 新規実装は必ず準拠 → (c) 既存は「見た目のみ・挙動不変」
スライスで段階的にクラス化（ルール7どおりリファクタ専用フェーズ・GOLDEN 再採取を伴う）。
絵文字は「タブ相当の主要導線のみ付ける」等の二値ルールにする。

### 🟡-4 対局管理タブのヘルプ欠落
HELP_TEXTS は 6 topic（first-round/report/reg/standings/master/save-warning）あるが、
**一番操作が複雑な対局管理タブの全体ヘルプ（再生成とリセットの違い・手合い変更・確定の意味）が無い**。
クラウド送受信のヘルプも無い（前回レビュー U-7 未対応のまま）。
**処方**: 'tournament' と 'cloud' の 2 topic 追加（実装済みのヘルプ定石 #307 に乗るだけ・低リスク）。

### 🟡-5 app/ と当日アプリの体験分断
配色・ヘッダ・ボタン様式が別アプリに見える（導線リンク自体は ?v=10 相互ナビで実装済み）。
**処方**: PWA 統合方針（1つの器）に合わせ、app/ の primary 色を #1F3864 に寄せ、共通ヘッダ様式を定義。
STYLE-GUIDE 制定（🔵-1）とセットで実施。

### 🟡-6 タップ目標 44px の全面適用（U-3 の残り）
min-height:44px が一部ボタンのみ。スマホ当日運営アプリとしては全ボタンに適用したい。
**処方**: `.btn{min-height:44px}` 系の共通 CSS 1 箇所で解決できるか検証（CSS 変更はルール3に注意・見た目スライス）。

### 🟡-7 参加者登録タブの情報密度
直下ボタン 7 個＋動的行。「クラス管理」「回戦数」「参加者登録」「過去参加者」が縦に並び初見の圧が強い。
**処方**: 名簿メンテで成功した **details 格納パターン**を展開（例: クラス管理・回戦数は「⚙大会の設定」に格納。
将来の「大会プロファイル」（汎用化 G1）と同じ置き場になるので二度手間にならない）。

## 4. 🔵 あったらいいもの（新設）

### 🔵-1 ★★ UI 規約の正本 `docs/STYLE-GUIDE.md`（最重要・最優先）
「継ぎ接ぎ」の根本原因は、**コードには正本（REFERENCE.md）があるのに UI には正本が無い**こと。
AI がスライスごとに UI を作ると、その都度ローカル最適な色・文言・通知を選んでしまう。
通知4分類（🟡-1）・保存系の呼称（🟡-2）・色/ボタン/絵文字ルール（🟡-3）・確認文体・ヘルプ定石を
1 ファイルに集約し、**CLAUDE.md/AGENTS.md から参照させて全スライスとレビューの必須チェック項目にする**。
これ1枚で「今後の継ぎ接ぎの再発」が構造的に止まる。コード変更ゼロで今日から効く。

### 🔵-2 保存状態バー（🟡-2 の実装形）
4系統の最終実行時刻を1行表示。「保存されているか不安」という当日運営の根源的不安を消す。

### 🔵-3 デモモード／サンプルデータ
架空16名のワンタップ投入（テスト fixture 流用）。新しい幹事の練習・他支部への売り込みデモ・
新機能の動作確認が全部これで楽になる。全国展開（P3）の前提装備でもある。

### 🔵-4 スクリーンショット付きマニュアルの更新体制
manual_sp/manual_print は文字中心。Playwright があるので**スクショ自動採取→マニュアル貼付**を
リリース手順に組み込めば、画面変更のたびにマニュアルが古くなる問題も解ける。

### 🔵-5 （将来・ロードマップ側）ライブページ・マイページ等
[汎用化ロードマップ](20260702_shogi_generalization_roadmap_v0.md) G3/G4 参照。本監査のスコープ外。

## 5. ジャンプアップの足がかり — 推奨実行順

```
Step 0（今日・コード変更なし）: repo 直下の patch 残骸を archive/ へ ＝ 🔴-1
Step 1（今週・docs-only）    : STYLE-GUIDE.md 制定 ＝ 🔵-1 ★ここが分水嶺
Step 2（小スライス×2）       : ヘルプ 2 topic 追加（tournament/cloud）＝ 🟡-4
Step 3（1スライス）          : 保存状態バー ＝ 🟡-2/🔵-2
Step 4（タブごとに段階実施）  : 通知手段の統一置換 ＝ 🟡-1
Step 5（見た目のみスライス）  : インラインstyle のクラス化・44px・app/ 配色統一 ＝ 🟡-3/5/6
Step 6                       : デモモード ＝ 🔵-3（全国展開 P3 の前提）
```

- Step 1 だけは順番を守る価値がある（以後の全スライスの品質が変わる）。
- Step 4/5 は挙動・見た目の変更を含むため、9項目ルール（リファクタ分離・GOLDEN 再採取・テスト維持）に
  従い1画面=1スライスで刻む。
- 前回レビュー（2026-06-24）の指摘は S-1/U-1/U-2/A-1/U-4 対応済み。残は U-3（44px全面）・U-7（cloudヘルプ）・
  S-2（Supabase 設定側）で、本監査の 🟡-4/🟡-6 に吸収した。
