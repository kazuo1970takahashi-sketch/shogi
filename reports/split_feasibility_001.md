- 依頼: `ai-requests/2026-07-28_claude-code_split-feasibility-001.md`（cowork・作者承認済み・調査のみ）

- 調査基準点: orphan clean base `2dc69eb`（`shogi_v4.html` = 1,102,033 bytes / 16,667 行 / sha256 `e88ed0d4…`）
- **アプリコードは一切変更していない。** 実験ビルドは使い捨て領域のみ（repo には本レポートだけ）

## 結論

**条件付き go。ただし「推奨する最初の一歩」は分割ではない。** 分割そのものは技術的にきれいに成立する — セクション境界で 48 パーツへ切り、`cat` 相当の単純連結で **元ファイルと byte 同一（sha256 一致）に戻せることを実証済み**（§2）。ES5・グローバル `state`・古典的クロージャは出荷物が同一である以上まったく変わらず、テスト 190 本／`run_tests.sh` 2,853 行も**無改修で通る**（§3）。にもかかわらず「開発スピードの次の1桁」は分割からは出ない：直近 20 スライスを「並行開発したら衝突したか」で実測したところ、**衝突 18/20 のうち 12 件（60%）は `test/run_tests.sh` 末尾追記と `docs/CHANGELOG.md` 冒頭追記だけの衝突**で、モノリスと無関係。残る `shogi_v4.html` 衝突 6 件は**6/6 とも両スライスが同一セクションを触っており**、セクション粒度で分割してもそのまま同じファイルの中で衝突する（§5）。つまり **実測した 18 件の衝突のうち、分割によって消えるものは 1 件も無い**（並行化効果 = ゼロ）。**最初の一歩は Stage 0＝調整ファイル（`run_tests.sh` / `CHANGELOG.md`）の追記点衝突の除去（1 スライス・低リスク・可逆）**を推奨する。これで観測された衝突の 60% が消える。分割に進むなら Stage A（ビルド導入＋文言/CSS 抽出）まで — 効果は「並行化」ではなく「**1MB の壁の解消**（GitHub Contents API がこのファイルを返せない事実は §4 で実測）」と「AI が読む単位の縮小」に読み替えるべきで、その目的でなら費用対効果は成立する。Stage C（UI/同期の分離）は効果の裏付けがないので**現時点では推奨しない**。

## 2. ビルド方式 — byte 同一は「実証済み」

### 2-1. 実験内容（使い捨て領域で実施・repo 不変）

`2dc69eb` の `shogi_v4.html` を、§1-2 のバナー境界で機械的に **48 パーツ**へ切り出し（`00_head_open.html` / `01_app.css.html` / `02_body.html` / `03_js_prologue.js` / 各セクション `.js` / `99_tail.html`）、**`cat` 相当の単純連結**（`Buffer.concat`）でビルドした。

```
パーツ数   : 48
元ファイル : 1,102,033 bytes  sha256=e88ed0d42ef58262aae11bfe4270cff1a7dead662a629106f093d0ace0b6c5e1
ビルド出力 : 1,102,033 bytes  sha256=e88ed0d42ef58262aae11bfe4270cff1a7dead662a629106f093d0ace0b6c5e1
byte 同一  : ✅ YES
```

**初回移行でビルド出力を現行ファイルと byte 同一にできる＝golden 同値証明は可能**（`sha256` 一致 1 行で証明が終わる）。これは「連結のみ・整形もトランスパイルもしない」から自明に成立する性質で、minify や module wrapper を一切入れないことが条件。

### 2-2. パーツのサイズ分布

| 指標 | 値 |
|---|---|
| 最大パーツ | 168,851 bytes（`RENDER`） |
| 100 KB 超のパーツ | **1 本のみ** |
| 中央値 | 8,843 bytes |
| 最小 | 26 bytes |
| **1 MB 超** | **0 本** |

### 2-3. 最小構成（ES5 維持・フレームワークなし）

```
src/
  MANIFEST            # 連結順を明示列挙（glob でなく明示＝並び替え事故を防ぐ）
  00_head_open.html
  01_app.css.html
  ...
scripts/build.sh      # 実体は「MANIFEST の順に cat」だけ（数行）
```

**必須の付帯ゲート**: 「`build.sh` の出力 sha256 == コミット済み `shogi_v4.html` の sha256」を `run_tests.sh` に 1 本追加する。これが無いと、`shogi_v4.html` を直接編集する習慣（CLAUDE.md 拘束ルール 8「編集対象は `shogi_v4.html`」）と衝突して**サイレントに乖離する**。これは分割の最大の運用リスク。

### 2-4. 拘束ルール 4 との関係（要 作者裁定）

CLAUDE.md / AGENTS.md の拘束ルール 4 は「**ES5 / 古典的クロージャ / グローバル `state` を維持（モジュール化・フレームワーク化しない）**」。本方式は**出荷物が byte 同一**なので実行時の性質は 1mm も変わらないが、*ソースの物理配置*は変わる。ルール 4 の文言をそのまま読むと抵触する（＝ Codex が P0/P1 を出しうる）。**分割に進む場合、ルール 4 の但し書き追記（「出荷物が byte 同一である連結ビルドは対象外」）が前提条件**。

## 3. テスト資産への影響 — 「ビルド出力をコミットする」なら**改修ゼロ**

- `run_tests.sh` は 2,853 行、`test/` 配下 190 ファイル。すべて第1引数 `$TARGET`（既定 `shogi_v4.html`）に対して動く。
- 各テストの読み方は 3 種で、いずれも**ビルド後の 1 ファイル**を前提にしている:
  - `fs.readFileSync(target)` ＋ `extractScripts()`（`<script>` 正規表現）→ `new Function(...)` で評価
  - `extractFunction(name)`（RAW からの波括弧バランス切り出し）
  - `grep -c "^function fn("` / `grep -q "文言"` 等の静的ピン（DOC-SYNC-001・MANUAL-SYNC-001 ゲート含む）
- **ビルド出力が byte 同一である以上、これら全部がそのまま成立する。** e2e（Playwright・`test/e2e/`）と `.github/workflows/e2e.yml`（`bash test/run_tests.sh shogi_v4.html` を実行し `FAIL=0` をゲート）も同様。

必要な改修は **追加 1 本だけ**:

| 追加 | 内容 |
|---|---|
| build drift ゲート | `scripts/build.sh` の出力と `shogi_v4.html` の sha256 一致を `run_tests.sh` で検査（不一致は FAIL） |

**ビルド出力をコミットしない設計（`.gitignore`）にすると話が変わる**: `run_tests.sh` / CI / e2e / html-validate すべてに「先に build する」前段が要り、`?v=N` の release 手順も CI 生成物前提になる。**推奨は「ビルド出力もコミットする」**（改修 1 本で済む・可逆・release 手順不変）。ただしその場合 §4 の「1MB の壁」は**解けない**（後述のトレードオフ）。

## 4. 運用への影響

### 4-1. リリース手順（`?v=N` / sw bump / production 反映）

ビルド出力をコミットする方式なら **変化なし**。release PR（base=production）は従来どおり `index.html` + `shogi_v4.html` の 2 ファイルを載せる。GitHub Pages が配る実体も同一 byte。

### 4-2. 「1MB の壁」— 実測で確認した事実

GitHub Contents API でこのファイルを取得すると:

```
File shogi_v4.html is too large to display (1102033 bytes).
Use the download URL to fetch the content: https://raw.githubusercontent.com/.../shogi_v4.html
```

GitHub の仕様は「**1 MB 以下 = 全機能サポート／1–100 MB = raw メディアタイプのみ**」。`shogi_v4.html` は 1.05 MB で**この境界のすぐ外**にいる。つまり Contents API 経由でしか読めないツール・エージェントは、この 1 ファイルだけ raw URL 迂回が要る。分割後は最大パーツ 165 KB・中央値 8.6 KB で、**全パーツが 1 MB 以下＝迂回不要**になる。

ただし **`git push`（HTTPS）にはこのサイズ制限は無い** — 本調査と同日、当セッションから同 repo へ 1.1 MB の `shogi_v4.html` を含む commit を通常どおり push できている（`81703c5`）。また MCP の `push_files` は Git Trees/Blob API（100 MB まで）を使う。**したがって「bundle 儀式」の根拠がもし *push が通らない* ことなら、それは現在の環境では成立しない**（repo 直下の `*.bundle` 3 本はいずれも 9–18 KB の旧世代の受け渡し遺物）。根拠が *Contents API で読めない* ことなら、分割は有効に効く。**この 2 つのどちらが実際の儀式の理由かは作者確認が必要**（本調査では前者は反証、後者は実証、という段階まで）。

### 4-3. トレードオフ（重要）

| 方式 | 1MB の壁 | テスト改修 | release 手順 | PR 差分 |
|---|---|---|---|---|
| **A: ビルド出力もコミット** | **解けない**（1.1 MB のファイルは repo に残る） | 1 本追加のみ | 不変 | **約 2 倍**（パーツ差分＋生成物差分の両方が載る） |
| **B: ビルド出力は gitignore（release/CI で生成）** | 解ける（開発ブランチに 1MB ファイルが無い） | `run_tests.sh` / e2e / CI / html-validate に build 前段が必要 | release PR が生成物を載せる形へ変更 | パーツ差分のみ（レビューは読みやすい） |

方式 A は「効果（1MB の壁の解消）が出ないのに差分が 2 倍になる」ため、**分割の主目的が 1MB の壁なら方式 B しか意味が無い**。方式 B は AGENTS.md の「レビュー対象 = `shogi_v4.html`」という前提そのものの改訂（レビュー対象 = `src/` パーツ）を伴う。

## 5. 並行化効果の実績ベース試算 — **効果は薄い（正直な結論）**

### 5-1. 測定方法

直近 30 スライス（`#692`〜`#790` 相当・`shogi_v4.html` を触った squash commit）について、`git diff -U0` のハンク行を各コミット時点のセクションへ写像した。さらに直近 20 の**隣接ペア**について「後発スライスを先行スライスの親へ `cherry-pick` で載せ替える」＝**両者を同一 base から並行開発した場合の衝突**を実測した。

### 5-2. 変更頻度（30 スライス中に触られた回数）

| 回数 | 単位 | 回数 | 単位 |
|---:|---|---:|---|
| 16 | `[JS] CLASS-VARIABLE-001`（受付コア） | 6 | `[JS] PLAYER-SWAP-001` |
| 14 | **`[CSS] <style>`** | 4 | `[JS] MASTER TAB` |
| 13 | `[JS] RENDER`（対局管理） | 3 | `[JS] BRANCH MASTER SYNC` |
| 12 | **`[HTML] body/head`** | 3 | `[JS] SCOREBOARD-MY-VIEW-001` |
| 9 | `[JS] PAST PARTICIPANTS PANEL` | 2 | `[JS] UTILITY` ほか |
| 7 | `[JS] INIT` | | |

**1 スライスが触るセクション数は平均 3.5**（分布: 1 セクション 5 件／2 が 8 件／3 が 8 件／4 以上 9 件・最大 12）。**分割しても「1 スライス = 1 ファイル」にはならず、平均 3.5 ファイルを跨ぐ。**

**セクション粒度でのペア衝突率 = 62.1%**（30 スライス・435 ペア中 270 ペアが同一セクションを共有）。**43 ファイルに割っても、任意の 2 スライスの 6 割は同じファイルに当たる**（CSS と body マークアップが半数近くのスライスで触られるため）。

### 5-3. 「並行開発したら実際に git 衝突したか」（隣接 20 ペア・実測）

| 結果 | 件数 | 割合 |
|---|---:|---:|
| クリーンにマージできた | 2 | 10% |
| **`test/run_tests.sh` / `docs/CHANGELOG.md`（＋`STYLE-GUIDE.md`）の追記点だけで衝突** | **12** | **60%** |
| `shogi_v4.html` で衝突 | 6 | 30% |

さらに、**`shogi_v4.html` で衝突した 6 ペアは 6/6 とも両側が同一セクションを触っていた**:

| ペア | 共有していたセクション |
|---|---|
| `175555f` × `2dc69eb` | CLASS-VARIABLE-001 |
| `c12314b` × `175555f` | CLASS-VARIABLE-001 / UTILITY |
| `a7f7821` × `c12314b` | HTML / BULK-ENTRY-001 / CLASS-VARIABLE-001 |
| `617de26` × `0ae7625` | UTILITY / RENDER 2 種 |
| `b72bb62` × `617de26` | RENDER |
| `af428d1` × `05fe640` | CSS / CLASS-VARIABLE-001 |

これは理屈どおりで、**git の衝突はそもそも「行が隣接している」ときにしか起きない**＝衝突するペアは定義上ほぼ必ず同じコード領域を触っている＝ファイルを割っても同じファイルに入る。

補足として、**いま実際に並行していた 2 ペア**（同一 merge-base のライブブランチ）を `git merge-tree` で検証すると、**両方ともクリーンにマージできた**（`feat/765` × `chore/l2-sweep-02` / `feat/763-player-swap-002` × `feat/auto-merge-gate-001`）。1.1 MB のモノリスでも、違う機能を触る限り git は普通にマージできている。

### 5-4. 「並行 N 本で衝突しない確率」の概算

ペア衝突率 p を用いて、N 本が互いに無衝突である確率 ≒ (1−p)^{N(N−1)/2}:

| | 現状<br>実測 p=0.90（20 ペア中 18 衝突） | **分割のみ**<br>p=0.90（**変化なし** — §5-3 のとおり衝突 18 件のうち分割で消えるものが 1 件も無い） | **Stage 0 のみ**<br>p=0.30（調整ファイル衝突 12 件が消え、残るのは HTML 衝突 6 件） | 分割 ＋ Stage 0<br>p=0.30（分割の寄与は 0） |
|---|---:|---:|---:|---:|
| N=2 | 10% | 10% | **70%** | 70% |
| N=3 | 0.1% | 0.1% | **34%** | 34% |
| N=4 | 0.0% | 0.0% | **12%** | 12% |

**「分割のみ」の列が現状とまったく同じになることがこの調査の核心**。並行度を上げる効果は **Stage 0（調整ファイルの追記点解消）に全部ある**。

なお隣接ペアは「直後のスライスが直前のスライスの後始末をしている」ケース（例: `l2-sweep` が直前機能を掃除する）を多く含むため、**p=0.90 は最悪ケース寄りの推定**。無作為ペアで見た同一セクション共有率は 62.1%（§5-2）で、こちらを上限に取っても結論（分割の寄与がゼロ）は変わらない。

|---|---|---|---|---|---|
| **Stage 0**（推奨・最初の一歩） | `test/run_tests.sh` の末尾追記を**ファイル走査（`test/test_*.js` を発見して自動実行）**へ変更／`docs/CHANGELOG.md` を**スライス 1 件 = 1 ファイル**（`docs/changelog/YYYYMMDD_<slug>.md`）へ分解し本体は索引化 | **1 スライス** | 低（テスト本体は不変・走査漏れは「本数が減っていないこと」で検査） | revert 1 本 | **観測された並行衝突の 60% が消える**（p=0.90→0.30） |
| **Stage A** | `src/` へ 48 パーツ分割＋`scripts/build.sh`（cat）＋sha256 drift ゲート。まず **CSS / body マークアップ / 印刷テンプレ / 文言（`HELP_TEXTS`）** の 4 パーツ相当だけを外に出し、JS 本体は 1 パーツのままでも可 | 2 スライス（PoC 済みのため実装は薄い。ルール 4 の但し書き改訂＋AGENTS.md のレビュー対象定義の裁定を含む） | 中（**サイレント乖離**が唯一かつ最大のリスク → drift ゲートで機械検出） | パーツを捨てて `shogi_v4.html` を正本に戻すだけ（byte 同一なので無傷） | 1MB の壁の解消（**方式 B を採る場合のみ**）・AI が読む単位の縮小 |
| **Stage B** | 純関数層（262 本・3,210 行）を `src/pure/` へ集約 | 2–3 スライス | 中（関数の移動＝行の大移動で、進行中ブランチ全部が rebase 衝突する。**他ブランチが空のタイミングでしか実施できない**） | revert（byte 同一が保たれる限り安全） | テスト・レビューの読解単位が小さくなる。並行化効果は §5 のとおり期待できない |
| **Stage C** | UI 描画・クラウド同期の分離 | 4+ スライス | **高**（`state`/`document` 直参照が 30%/27%・build/bind/coordinator パターンの境界とセクション境界が一致しない） | 同上 | **裏付けなし。現時点では推奨しない** |

**中断可否**: Stage 0 / A / B はいずれも単独で出荷でき、次段階に進まなくても損失は無い（出荷物が byte 同一なので production 影響ゼロ）。Stage B は「他の作業ブランチが無いタイミング」という実施窓が要る点だけが不可逆的な制約。

## 付録: 測定の再現手順（すべて read-only）

| 測定 | 手段 |
|---|---|
| 構造棚卸し（§1） | `shogi_v4.html` の `<style>`/`<script>` 境界とバナーコメント（`// ====` sandwich）を走査。トップレベル関数は波括弧バランスで抽出（テスト側 `extractFunction` と同方式） |
| 結合点（§1-3） | 各関数本体に `state` / `document` / `window` / `localStorage` / `master` が現れるかを機械判定 |
| byte 同一 PoC（§2） | 48 パーツへ切り出し → `Buffer.concat` → `shasum -a 256` 比較（使い捨て領域・repo 不変） |
| 変更頻度・ペア衝突（§5-2） | 直近 30 コミットの `git diff -U0` ハンクを、そのコミット時点のセクション表へ写像 |
| 並行衝突の実測（§5-3） | 隣接 20 ペアで「後発スライスを先行スライスの親へ `git cherry-pick`」→ 衝突ファイルを分類。ライブブランチは `git merge-tree --write-tree` |
| 1MB の壁（§4-2） | GitHub Contents API で `shogi_v4.html` を取得し "too large to display (1102033 bytes)" を確認 |

### この調査の限界

- §5-3 の並行衝突シミュレーションは「後発スライスを 1 段だけ載せ替える」近似。実際の並行開発では両側が同時に育つため、衝突はやや増える方向に振れうる（ただし**衝突ペアが同一セクションを共有するという性質**は変わらない）。
- サンプルは直近 20 隣接ペア＋実ライブ 2 ペア。統計的にタイトではないが、60%/30%/10% の内訳は一貫していた。
- §4-2 の「bundle 儀式」の廃止可否は、儀式の根拠が *push 不能* か *Contents API で読めない* かで結論が反転する（前者は反証済み・後者は実証済み）。**作者確認が必要**。
